Anvil: An IDE Where the Engineer Designs and the AI Types

A VS Code fork for experienced developers who want AI leverage without surrendering architectural control. (Anvil is a working title.)

01Abstract

Current AI coding tools push toward delegation: describe a feature, receive hundreds of lines, review what you can. That workflow suits prototyping. It is a poor fit for engineers who own a system, hold its architecture in their heads, and are accountable for every line that ships.

Anvil inverts the relationship. The engineer designs every part of the program. The AI performs only the typing. It does not propose unrequested code, does not plan on the engineer's behalf, and does not produce output larger than what was asked for. Interaction happens inline, at the cursor, in two modes: a command mode that makes a small, scoped edit and stops, and a query mode that answers questions and never touches the file.

The goal is not a better model. It is a better contract between developer and model, one that makes guesswork in a project close to negligible while still using AI heavily.

02The problem

Where today's tools fall short for experienced engineers

  • Unsolicited suggestions. Ghost-text completion interrupts thought. The engineer must read and reject code they never asked for, which costs attention even when the suggestion is wrong.
  • Prompt-and-select workflows. Highlighting code, opening a side panel and writing a paragraph breaks flow and invites the model to rewrite more than intended.
  • Large, hard-to-review diffs. A model that returns fifty lines for a ten-line request makes review slower than writing the code by hand.
  • Weak grounding. Models guess at types, signatures and conventions when they are given loose text context. Guessing produces plausible but wrong code.
  • Eroded ownership. When the AI decides structure, the engineer stops being the author of the design, and the codebase drifts from any single coherent mind.

03Design principles

  1. The engineer is the architect. The tool never decides structure, naming strategy, or module boundaries unless asked a specific question about them.
  2. Silence by default. No ghost text, no popups, no proactive suggestions. The AI speaks only when invoked.
  3. Small, scoped, then sleep. Every command produces the minimum edit that satisfies the request, shows it, and stops.
  4. Ground in facts, not vibes. Context comes from the language server and syntax tree: real types, real signatures, real call sites.
  5. Edits and answers never mix. A question cannot modify code. A command cannot start a conversation.
  6. Everything is reversible in one step. One generation is one undo.
  7. Model-agnostic. The value is in the interaction and context layers, not in any particular model.

04Interaction model

All interaction happens inline, in the editor, at the line being worked on. There is no chat sidebar in the primary workflow.

Command mode (edit)

The engineer types a command sentinel and presses Enter. An input box opens in place of that line. They describe a small, specific change in plain language. The model returns a scoped edit, the editor applies it, and the input closes.

// cursor on an empty line inside handleEvent()
%^&  ← Enter
│ switch on event.kind, one case per EventKind variant, call dispatch(event, ctx) in each │

// result: one block, exactly where the cursor was, then the tool goes quiet
switch (event.kind) {
  case EventKind.Open:  dispatch(event, ctx); break;
  case EventKind.Close: dispatch(event, ctx); break;
  case EventKind.Error: dispatch(event, ctx); break;
}

Query mode (ask)

A second sentinel opens the same inline box, but in conversational mode. The engineer can ask what a function does, why an API behaves a certain way, or what the tradeoffs of an approach are. The answer renders inline or in a transient peek view. No edit is ever applied in this mode.

$%#  ← Enter
│ why does this retry loop not back off on 429? │

Sentinels

The default sentinels (%^& for command, $%# for query) are fully configurable. They are intercepted by the editor's input handler and removed from the buffer the moment they are recognised, so they never appear in the saved file. Some sequences collide with real syntax in certain languages (shell and Perl use $%# constructs), so Anvil also supports dedicated keybindings as an alternative, and sentinel recognition can be limited to an otherwise empty line or comment context.

Rule of the contract: the engineer states what and where; the AI supplies only the keystrokes. If a request implies a larger design decision, the tool asks or declines rather than deciding.

05System architecture

+-----------------------------------------------------------+ | Anvil (VS Code fork) | | | | Editor core (Monaco) | | |-- Sentinel interceptor (type handler / keybinding) | | |-- Inline prompt widget (content widget at cursor) | | |-- Edit applier (single undo stop, diff) | | '-- Inline suggestions (DISABLED / removed) | | | | Anvil service (built-in, part of the IDE itself) | | |-- Mode router (command vs query) | | |-- Context engine (LSP + tree-sitter + index) | | |-- Constraint layer (scope, size, schema checks) | | '-- Model gateway (provider adapters) | +---------------------------|-------------------------------+ v Hosted model API / local model (Ollama, llama.cpp)

The flow for a command is: intercept sentinel, capture cursor position and typed instruction, resolve referenced symbols through the context engine, build a narrow prompt, request a structured edit from the model, validate it against the constraint layer, and apply it as one undoable operation.

06The context engine

This is where "negligible guesswork" is won or lost. A small instruction only works if the model is handed exact facts about every symbol the instruction mentions.

What gets gathered

  • Enclosing scope: the function or block at the cursor, the local variables in scope and their inferred types.
  • Mentioned symbols: any identifier in the instruction is resolved through the language server to its definition: signature, type, doc comment, and a few representative call sites.
  • Local conventions: neighbouring code in the same file for naming, error handling and formatting style.
  • Project rules: an optional .anvil/rules.md where the team states hard conventions, read on every request.

How it is gathered

SourceProvidesMechanism
Language serverDefinitions, types, signatures, references, diagnosticsVS Code language-feature commands such as vscode.executeDefinitionProvider, executeHoverProvider, executeReferenceProvider
Syntax treeExact scope boundaries, statement and block rangestree-sitter (WASM), for an error-tolerant parse of incomplete code
Project index (later)Cross-file symbol lookup when the LSP is slow or absentLocal symbol index built from tree-sitter tags queries
Rules fileTeam conventionsPlain markdown read from the workspace

The prompt contains only what the instruction needs. Smaller, more precise context also means lower cost, lower latency and fewer opportunities for the model to wander.

07Enforcing restraint

"Generate it and go to sleep" cannot depend on a polite system prompt. It has to be enforced in code, around the model.

  • Structured output. The model must return an edit object, not free text. Example shape: { "range": ..., "replacement": "...", "needs_clarification": false }. Anything that does not parse is rejected.
  • Scope lock. The edit may only touch the range at the cursor, or the selection or block it was invoked on. Edits outside that range are discarded.
  • Size budget. A configurable cap on lines and tokens. If the model exceeds it, the edit is refused and the engineer is told the request is too large for this mode, rather than being shown a huge diff.
  • Clarify, don't guess. If a referenced symbol cannot be resolved or the instruction is ambiguous, the model returns needs_clarification with one short question instead of inventing an answer.
  • Post-edit checks. After applying, wait for diagnostics from the language server. New errors on the edited range can be surfaced immediately, so the engineer finds out about hallucinated symbols in seconds.
  • One undo step. The edit is applied as a single operation with undo stops on both sides, so one keystroke reverts it.
  • Mode isolation. Query mode is not given any edit capability at all; command mode is not given a conversational channel.

09How to build it

Anvil is built as a standalone IDE from the first commit. There is no extension stage: the prototype is an early build of the product itself, so what gets tested is the real thing, running in its own environment.

Phase 0: Fork skeleton (1 to 2 weeks)

  • Fork microsoft/vscode, build it from source, and get a branded dev build running on your machine.
  • Edit product.json: name, application and data-folder identifiers, extension gallery pointed at Open VSX, telemetry endpoints removed.
  • Give the build its own user-data and extensions directories so it never reads or modifies an existing VS Code setup.
  • Keep your changes isolated in a few clearly named directories to ease future rebases.

Phase 1: Thin prototype inside the fork (2 to 3 weeks)

  • Implement the smallest end-to-end slice of command mode: intercept the sentinel in the editor, remove it from the buffer, open a basic inline input, send the instruction plus the enclosing function to one model provider, and apply the returned edit.
  • Turn off inline suggestions in the default configuration ("editor.inlineSuggest.enabled": false) for now; Phase 2 removes the feature properly.
  • Rough edges are fine here. The point is to dogfood the loop on a real project for a week, because if the interaction does not feel better than what you use today, that is what needs fixing before anything else.

Phase 2: Polished native inline prompt (3 to 5 weeks)

  • Implement the sentinel interceptor at the editor level (type handler) so it is instant and does not flicker the buffer.
  • Build the inline input as a Monaco content widget or view zone, with proper focus handling, Escape to cancel, and Enter to submit.
  • Remove or compile out the inline-suggestion contribution so ghost text cannot be re-enabled by accident.

Phase 3: Context engine (4 to 6 weeks)

  • Integrate web-tree-sitter for the main target languages first (pick two or three, not twenty).
  • Implement symbol resolution through language-feature commands, with caching and timeouts so a slow server never blocks the editor.
  • Add the rules-file loader and a context budget so prompts stay small.

Phase 4: Constraint layer (2 to 3 weeks)

  • Define the edit schema and validator, the scope lock and the size budget.
  • Implement clarification responses and post-edit diagnostics checks.
  • Make each generation a single undo operation.

Phase 5: Query mode (2 to 3 weeks)

  • Same inline box, separate pipeline with read-only context and no edit capability.
  • Render answers inline or in a peek view; allow follow-up questions in the same box.

Phase 6: Hardening and release

  • Provider adapters for hosted and local models, keychain-based key storage, offline behaviour.
  • Signed installers for Windows, macOS and Linux, plus an update channel.
  • Logging that is local only and opt-in; documentation aimed at engineers, not beginners.
Realistic scope: one engineer can reach a usable alpha in roughly four to six months of focused work. Most of the effort goes into the context engine and the editor integration, not the model calls.

10Living with a fork

  • Rebasing. VS Code ships monthly. Keep your patch set small and well-isolated, and track upstream on a regular schedule instead of letting the gap grow.
  • Licensing. The source repository is MIT-licensed, but Microsoft's distributed "Visual Studio Code" binary carries a separate licence, and its Marketplace and some proprietary components (certain remote-development and C# tooling) are restricted. Build from source, use your own name and branding, and use Open VSX. Have the specifics reviewed before a public release.
  • Extension compatibility. Most extensions work on Open VSX, but some popular ones are Marketplace-only. Check the ones your users depend on.
  • Isolation from existing setups. Anvil installs and runs separately, with its own settings, extensions and data folders. Developers keep their existing VS Code environments untouched and can trial Anvil alongside them. A one-time import of settings, keybindings and a chosen set of extensions can be offered as a convenience.

Build a small replayable benchmark from real instructions in real repositories early, so that changes to prompts, context rules or models can be compared objectively.

12Risks and open questions

  • Latency. Inline flow dies if results take ten seconds. Small context and small outputs help; a fast model tier may be needed for command mode.
  • Language server quality varies. Dynamic languages give weaker type information. Tree-sitter and call-site examples partly compensate.
  • Sentinel ergonomics. Typed sentinels might feel clumsy compared with a single hotkey. Test both with real users.
  • Where the line sits. The boundary between "typing" and "designing" will need tuning. Too strict is frustrating; too loose recreates the problem.
  • Market size. The target audience is narrow by design. That is acceptable for a project of this kind, but it shapes how it should be funded and distributed.
  • Privacy expectations. Sending code to a hosted API is a real concern for some teams. A local-model path should be a first-class option, not an afterthought.

13Non-goals

  • Training or hosting a frontier model.
  • Autonomous multi-file agents that plan and execute features on their own.
  • Ghost-text autocomplete in any form.
  • Serving beginners or "describe an app and get an app" workflows.
  • Replacing the engineer's judgement about architecture.
